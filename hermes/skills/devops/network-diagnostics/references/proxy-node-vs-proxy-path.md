# 代理路径与出口节点分层诊断

## 适用场景

同一服务出现以下矛盾现象：直连超时、当前代理TLS失败、备用公共域名可用，或用户怀疑“到底该走代理还是直连”。

## 核心原则

“代理失败”至少可能是三种不同问题：

- 本地代理端口或协议不可用；
- 当前策略组把域名错误路由为DIRECT；
- 代理本身正常，但当前出口节点因地域政策、上游封锁或节点质量无法访问目标。

必须做节点级对照，不能只比较一次“直连 vs 当前代理”。

## 最小复现流程

1. 检查环境代理、Windows系统代理、监听端口和进程归属。
2. 用控制站点验证代理端口：Google `generate_204`等。
3. 对目标服务执行强制直连和显式代理测试，记录HTTP码与耗时。
4. 如果控制站点正常而目标失败，读取代理策略组当前选择。
5. 临时轮换多个地区节点；每个节点测试目标服务的所有关键端点。
6. 使用`try/finally`恢复原节点。
7. 只有在用户明确授权后，才永久修改策略组或规则。

## Clash/Mihomo控制器伪代码

```python
original = get_selector("Proxies")
try:
    for node in ["HK", "JP", "SG", "US", "TW"]:
        set_selector("Proxies", node)
        test("https://service.example/ping")
finally:
    set_selector("Proxies", original)
```

控制器可能要求Bearer secret。读取本机配置即可，禁止在报告中回显订阅URL、节点凭据或控制器secret。

## 结果判读实例

一次实测中：

- 直连目标服务：超时；
- 当前台湾节点：TLS握手失败；
- 香港、日本、新加坡节点：HTTP 200；
- 美国节点：HTTP 451；
- 同一代理端口访问Google：HTTP 204。

正确结论是“应走代理，但当前台湾出口不适用；固定香港，日/新作为备用”，而不是“代理不能用”或“API密钥错误”。

## 交易所额外验收

公开Ping成功后，还要分别验证：

- 现货公开Ping；
- 合约公开Ping；
- 签名只读账户接口；
- 不得用下单、撤单作为连通性测试。

只有签名接口返回业务错误码时，才讨论Key、IP白名单、权限或时间戳；TLS失败、连接重置和超时发生在鉴权之前。
