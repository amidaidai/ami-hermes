# 视觉症状定位 + 版本容忍验证链（2026-09-10 实案）

> 触发场景：多轮迭代交付后，用户报**视觉症状**——「这两条线丫的好平啊」「线没了」「被压扁了」「看不到 X」。
> 本文件记录该类症状的**定位顺序**，以及支撑多轮迭代的**验证脚本写法**。

## 一、用户报「视觉症状」时的四步定位法（按信息量排序，别一上来改代码）

### 第 1 步：先读现场，不许猜

`tv_health_check` → `chart_get_state` → `pane_list` → `tab_list`。

20260910 实测：CDP 指到的图是 `OANDA:XAUUSD` 15m、只挂内置 Volume、`pane_list` 仅 1 个窗格、
`tab_list` 仅 1 个标签页 —— **用户看的是我够不到的另一处**。

**必须先把这件事说清楚**（「我看不到你的那张图」），再走下面的推理路径；
绝不能假装看到了症状就开始改代码。

### 第 2 步：用真实行情复现指标内部的数学，建立「本应长什么样」的基线

模板：`outputs/pine_20260905/cvd_flatness_probe_20260910.py` ——
从 Binance 拉 klines，**逐字复现**指标里的 delta / 累计 / 滚动和，输出「范围 / 均值 / 两者比例」。

本次结论（BTCUSDT 15m，500 根）：单根 delta 均值 131、`CumDelta` 范围 **4053**、
滚动和范围 **4858**、量级比 **1:1.2**。
→ **两条同量级的线不可能「自然」变平** ⇒ 「平」只可能来自「坐标被撑开」这一类原因。

**价值：把「猜测」变成「排除」**，一次砍掉一半候选原因，而且不消耗用户任何操作。

### 第 3 步：用「这个脚本能不能渲染」反推用户装的是哪个版本

编译期错误（如绘图 65/64）会让 TV **拒绝编译** ⇒ 那个版本**图上一个东西都画不出来**。

本次推理链：用户说「能看到两条线」⇒ 排除超限版（v5）⇒ 锁定最近一次改动（v6）
新增的唯一绘图对象（`line.new`）⇒ 就是它。

**这类推理比问用户快，且不用他动手。** 同类可用的判据：
- 报「编译错误」⇒ 该版本未上机
- 报「能看到 X」⇒ 该版本已上机且编译通过
- 报「X 不见了但 Y 在」⇒ 版本已上机，是 X 自身的条件/量纲问题

### 第 4 步：只在①②③指向同一层时才动代码

三次证据都指向同一处再改，否则就是拿用户的时间做实验（本次第 6 轮已因「聪明但没验证的省槽写法」翻车一次）。

## 二、震荡窗格里的坐标量纲禁令（本次根因）

副指标窗格是**震荡窗格**，Y 轴量纲是 Delta/CVD（±数千）；`low`/`high`/`close` 是**价格**量纲（BTC 数万）。

```pine
// ❌ 禁止：TV 把绘图对象纳入窗格自动缩放 → 窗格 Y 轴被撑到价格区间 → 全部曲线被压成平线
line.new(bar_index, low, bar_index, high, extend=extend.both, ...)

// ✅ 现行：bgcolor 与量纲无关，零缩放风险
bgcolor(cond ? color.new(chart.fg_color, 80) : na, title='...')
```

**机械自检（已固化为断言）**：

```bash
grep -nE '(line|label|box)\.new\(.*\b(low|high|close|open|hl2|hlc3)\b' 副指标.pine
```
副指标应为**空**（主指标挂在价格窗格，价格量纲合法）。

细节与省槽取舍见 `references/aggvol-plot-slot-crisis-20260910.md` 第 3.1 节。

## 三、版本容忍验证链（`verify_vN` 模式）

多轮迭代后，**早期断言会对新版本产生假失败**。20260910 一天内踩到三类，都必须提前设计：

| 假失败类型 | 症状 | 修法 |
|---|---|---|
| **设计被取代** | v5 断言「存在 `bgcolor(...)`」，v6 换成 `line` → FAIL | 写成 OR 容忍：`X_old in ac or X_new in ac` |
| **严格逐行等值** | 「除新增处外与上一版逐行一致」在改动更大的版本上必然 FAIL | 加**版本标记旁路**：`"<新版独有代码串>" in c5 or <逐行等值>` |
| **配额等值断言** | `v5m["plot"] == v4m["plot"] + 1`，v7 少一条 → FAIL | 改成**只卡上限** `b[k] <= hi`；**减少是好事**，功能损失交给专项断言 |

三条规矩：

1. `verify_vN` 必须**先回归 v2…v(N-1) 的全部断言**（子进程调用），再跑自己那组；任一层非 0 退出即整体失败。
2. **旁路条件必须用代码串，不能用注释做标记** —— 验证脚本普遍先做 `code_only()` 去注释，注释标记会被剥掉。
3. **视觉类改动必须新增「机制级反例断言」**，不能只写「我改好了」。
   本次新增的就是第二节那条 grep 规则。
   → **教训：上一轮事故对应的检查必须固化成断言，否则下一轮会重犯。**

推论：一套 `verify_v2…v7` 共 184 项断言的价值不在「都通过」，而在**每轮新事故都变成一条永久断言**。

## 四、交付口径（本轮再次踩到）

- **服务器编译 0 错 0 警 ≠ 客户端通过**：IL 上限、**绘图 64 上限**、窗格缩放，`translate_light` 一个都不检。
- 涉及「只有挂图才看得见」的修复，交付必须写明「此项只能由用户挂图验证」，
  并**给出用户要看的具体两点**（哪根轴、哪条线），不要只说「验证一下」。
- **失败/回退要直说「这是我的漏估 / 我的锅」，再给证据链**（用户是快进快出型，要的是定位与修法，不是免责）。
- 预判二次失败：给出「如果装了还是一样的症状，那就不是 X 而是 Y」的分支 + 需要用户提供什么
  （截图 / 品种周期模式 / 是否勾了叠加），避免再来一轮往返。
