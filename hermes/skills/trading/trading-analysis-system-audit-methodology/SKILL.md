# 交易分析系统全面审计方法论

## 适用范围

当用户要求全面审计交易系统、分析流程、策略、模板、分析档位、TradingView流程、分析卡或全系统优化时使用。覆盖运行态、代码、数据契约、TV指标、路由执行、最终裁决、模板投递与测试，不把单个脚本检查冒充全系统审计。

## 核心原则

1. **当前证据优先**：历史报告只能作为线索；先记录当前时间、仓库、分支、工作树和配置，再引用历史结论。
2. **能力存在不等于能力已使用**：分别判断已配置、可调用、已接线、已参与裁决、已在卡片呈现。
3. **心跳健康不等于业务健康**：进程、心跳、配置有效期、批准对象数量和业务事件必须一起检查。
4. **路由必须约束执行**：比较Router声明的步骤与执行器真实调用、评分输入和FinalVerdict消费。
5. **证据分层**：每条发现标记“当前复现/静态核对/未验证”，不把测试退出码等同于生产正确。
6. **决策单一真相源**：最终卡片、告警、仓位和执行只消费冻结快照与FinalVerdict。
7. **主指标授权、副指标确认**：SVP是唯一执行授权来源；AggVol只确认、降级或否决，不能单独授权。
8. **用户人工控制**：分析系统提供方向、触发、失效和候选价，不自动下单；WAIT/NO-GO不得渲染成执行单。

## 审计顺序

### 阶段一：基线与边界

- 确认canonical仓库和运行目录；读取项目规范、manifest、关键入口。
- 执行`git status --short --branch`，把既有修改与本轮产物分开。
- 检查是否存在归档目录、双脚本目录、多个数据目录和旧兼容路径。
- 明确本轮只审计还是允许修复；未经用户要求不要修改业务代码、提交或推送。

### 修复行动前的前提核验（避免错误 P0/错误修复）

给出「修复/拉起/补cron/提交删除」建议前先核验前提——否则会把「退役」误判成「崩溃」、把「历史状态」误判成「活跃故障」。三把核验锤：

1. **守护进程「退役 vs 崩溃」**：心跳停 ≠ 崩溃。先读脚本 `__main__`：若含 `已退役`/`退役`/`生产权威为` 等字样，说明是兼容壳、真实守护已替换（如 `scripts/行情守望.py` 退役 → 生产为 `keylevel_guard`）。此时心跳文件是旧守护遗留，页面「心跳旧」≠「进程死」。**否则会错误拉起一个只打印“已退役”的壳。**
2. **cron `enabled`/`state` 才是真相**：`hermes cron list` 的 `last_status=ok|error` 可能是禁用/暂停前的历史。读调度器配置（如 `cron/jobs.json`）的 `enabled`+`state`：`enabled:false` 或 `state:paused|disabled` = 不跑，其 error 属历史非活跃故障；不要据此补 cron 或“修复失败任务”。
3. **git 批量删除安全**：提交大量删除前交叉核验 ①启用 cron 的脚本是否指向被删文件 ②被删模块是否仍被活跃脚本 import（**含懒加载** `from X import` 缩进在函数内、以及**动态加载** `importlib.spec_from_file_location("X", ...)`）。活跃依赖方显式 `try/except ImportError` 兜底（如 orion 对 `alert_dedup`）则删安全；裸 import / 无兜底动态 spec → 先 `git checkout HEAD -- <file>` restore。

**守卫生成的非零退出可能是有意诚实信号，不是 bug**：如关键位批准过期（`valid_until` 已过）时看门狗报 `exit 2 / DEGRADED`，是“批准过期不下准生证”的如实上报；续期（把 `valid_until` 重设 `now+有效期`，同步 `updated_at`/renewed_at，备份后原子写）后其退出码转 0、调度器 `last_status` 转 ok。

### 阶段二：运行态健康

按顺序检查：

1. TV Desktop/CDP连接、当前symbol、周期和study列表；
2. 行情守望、BTC守护、关键位守护的真实进程数量；
3. 心跳时间、status、PID一致性；
4. keylevels配置是否存在至少一个未来有效且批准的关键位；
5. cron enabled/state/last_status/next_run、脚本路径和provider/model；
6. 数据文件的mtime、根时间戳、symbol匹配、JSON结构和语义完整性。

同一脚本出现多个Python节点时，先排除uv venv redirector stub父子节点，再判断真多实例。常驻while True进程不能配置为普通周期cron，必须使用daemon+watchdog或支持--once。

### 阶段三：分析管线与档位

对每个资产至少验证BTCUSDT、XAUUSD，并按项目声明扩展外汇、股票、期货、期权：

- `resolve_analysis_mode`触发词是否与文档一致；
- `route_pipeline`步数、主周期和资产分类是否正确；
- 档位以 `pipeline_router.py::ANALYSIS_TIERS` 为权威：quick/standard/full/monitor，inherit 为兼容别名；裸品种/看一下=L1，现在呢/更新/扫一下=L2，分析=L3硬开关；实际执行与输出范围须一致；
- inherit是否明确缓存时间、symbol和“继承”语义；
- quick跳过的数据是否仍偷偷进入评分；
- full每一步是否有独立完成/跳过/失败原因；
- XAU是否走专用同步与经核验的同源行情；不得默认用 Binance 加密合约替代 OANDA 黄金，也不得套用加密 Funding/Taker/OI。实际源与降级以当前 xau_tv_sync 代码和返回元数据为准；
- crypto是否真的接入K线、VWAP/EMA、TV五层和衍生品数据。

“Router打印3步但执行了10步”属于路由-执行漂移，至少P1；若被跳过的数据影响最终方向或等级，升级为P0。

配置隔离验收：读取 spec 不得改写共享 MODE_SPECS；修改返回的嵌套列表也不得污染后续请求。覆盖全部档位和异常档位。记忆只保留稳定规则与权威入口，不保存测试数量、实时行情、旧配额余量或历史上线结论。

### 逐档实跑可用性审计（不信声明，跑一遍）

档位文档只写「应该怎样」；**可用性必须实跑**。每个档位对同一品种各跑一次全文，
抓 `管线路由` / 每步的 `✅⚠️⏭️ℹ️` 行 / `管线完成度审计` 三段，再横向对比：

| 要点 | 判据 |
|---|---|
| 声明步数 vs 实际步数 | `route_pipeline(symbol, mode)` 才是权威；本轮 `quick` 与 `standard` 返回**同一列表** |
| 档位之间到底差什么 | standard 只多一行「继承高周期上下文 <时间戳>」，不是多跑步骤 |
| 「跳过」是哪一种 | 有意跳过（档位不够）走 `⏭️/ℹ️`；真实失败走 `⚠️`；两者**不能混为一谈** |
| 声明 scope 是否真落地 | L1 声明「主周期行动格+现价+一张截图」，实际仍渲染完整四表卡 → 声称的轻量化未落地 |
| 非用户档位 | monitor 无自然语言触发词；非加密品种 monitor 路由 **0 步** → 设计内，不是故障 |

- 结论写成「档位 × 步骤/来源」可用性矩阵，四类分开：**可用 / 有意跳过 / 真实失败 / 生产者退役**。
- 判「某源不可用」之前必须再做两件事：**绕过封装探原始上游端点**（见下节）与
  **确认当前是否还有写入方**（`grep` 该落盘路径：只有读取方、没有写入方 ⇒ 恒陈旧，恢复 cron 也治不好）。

### 阶段四：指标与TV流程

TV读取固定遵循：切目标symbol→等待指标重算→`chart_get_state`核对symbol+周期→读主指标行动格→读副指标行动格→读study values/lines→截全屏图→再次核对关键身份。

- 主指标过滤`SVP+ICT+VWAP+CVD`；副指标过滤`Volume Aggregated`。
- 截图必须含价格轴与CVD窗格；旧截图不能冒充本轮更新。
  **截图内容要读回验证**，不能只看文件存在 + 有字节：用视觉能力（`vision_analyze`）读回本轮截图，
  逐项确认 ① 品种/周期标签 ② 右侧价格轴可见 ③ 底部副窗格（CVD/AggVol）在位 ④ 价格与同日 Binance 值同量级。
  本轮实测这一步才发現：只能靠读回确认「AggVol 窗格在底部、CVD 字样只在主指标名里」，
  避免把「有截图」当成「截图合规」。
- 不把`study_values`缩写值当精确关键位；必要时用pine lines/labels。
- Pine云端编译没有真实回执时，只能写“未验证”。
- CVD若为K线方向或低周期估算，必须标注估算，不能写成交易所真实主动成交。
- 检查Packed Bus的合同号、Valid Code、Coverage、OI一致率、CVD质量和数据新鲜度是否被Python正确解码。

### 阶段五：决策与策略闭环

追踪完整链路：指标/采集写入→标准化快照→特征→体制→候选方案→闸门→FinalVerdict→渲染。

强制验证：

- `X禁做`必须NO-GO；
- `WAIT/NO-GO`必须`executable=false`且清空entry/stop/target；观察价只能放watch字段；
- B/C等待只能展示触发条件和人工候选，不得给执行损益指令；
- `R:R < 2.0`不得执行；
- 主副冲突、TV未现场验证、数据过期、zone质量不足和高级门控拒绝不能被后置渲染覆盖；
- 结论包含“观望/未收线/等解除/等收线/冲突”等C等待语义时，不能被数值Grade Code兜底改成A；
- 主指标与副指标方向冲突时，卡片不得出现“主副同向”。

必须使用矛盾夹具测试，而不只测正常A多路径：主指标X/冲突/未收线+AggVol S3、主副反向、A但RR不足、错symbol缓存、多源时间不一致、异常Max Pain。

### 阶段六：模板、卡片和投递

核对模板、renderer与FinalVerdict是否同一版本：

- 五周期D→4h→1h→15m→5m；
- 结构位先于价格；
- 只允许一个⭐主推；备选仅失效路径；
- 截图首行；结论、机会/陷阱/禁做和触发/失效前置；
- quick与full形态确实不同，而非只改标题；
- RichMarkdown真表格必须走专用发送器，不能用普通MarkdownV2假设会渲染管道表；
- 推送成功必须有真实回执，cron `ok`或stdout存在不等于用户可见。

### 阶段七：问题分级与整改

| 等级 | 判定 |
|---|---|
| P0 | 会导致错误方向/执行价、数据跨品种污染、关键守护空转、FinalVerdict被绕过、生产分析不可相信 |
| P1 | 显著降低完整性、覆盖率、可观测性或档位一致性，但有明确降级 |
| P2 | 可维护性、成本、审美、文档和非关键冗余优化 |

每个问题必须记录：证据路径/命令、当前结果、根因、影响、修复建议、验收标准、证据等级。不可引用不存在的字段，不可仅凭grep行号认定调用关系；命中后必须看上下文并追踪生产者到消费者。

## 审计证据的反例校核

- **不要把用户粘贴的总结或自己上一轮的结论当成本轮结论复述。** 用户贴多份互相矛盾的报告时，
  那是线索不是事实；逐条重新取证，发现不成立就明确写「撤回」并说明错在哪里（本轮实际撤回过一份
  自己写的综合报告：行数记混、缺包结论不成立、绝对化健康断言、引用不存在的截图）。
- 报告引用 `rr_a or rr_b` 时，非零0.547本身不会触发反侧兜底；必须追查传入闸门的实际payload、方向选择、调用时序，不能拿另一时刻JSONL数字证明同一调用发生覆盖。
- 既有修复仍需测显式0与旧别名并存、NaN/inf/非法字符串以及FinalVerdict与meta方向不一致。两条renderer共同测试有限正数、几何、等级、声明与实际R:R，避免只修闸门不修展示。
- 批准来源时间、候选采集时间、结构复核时间和TTL续期时间是不同事件，禁止为了“新鲜”将历史批准来源改成本轮时间。
- 分母分开：路由步骤数不等于来源数，有效完成不等于执行尝试。旧守护/旧影子日志需追到当前替代链再定级。
- 只读审计允许不切TV；此时不能称当前图表或云编译验证完成，也不需要把源码文件伪装成截图。

## 修复落地纪律（并行代理 · 降级落点 · 伪造默认值）

### 并行修复代理的交接纪律

用多个子代理并行改同一仓库时，**它们的中断是常态**（配额/超时/迭代耗尽），且常留下**半成品**：
测试失败、自己的新用例不通过、甚至改坏既有生产契约。本轮实测：4 个修复代理全部以
`HTTP 429 usage limit` 结束，其中一个把硬拦截写进 `check_constitution`，直接让 5 个既有生产测试失败。

- 代理「完成」的自述不可信：`status=completed` 可能只是 `exit_reason=max_iterations` + API 报错。
- 收工后必须 `git status`/`git diff` 逐文件核，再跑**全量**回归；只跑新用例会漏掉被改坏的旧契约。
- 破损处由主代理补完或回退，并在回复里写明为什么否掉子代理的方案。
- 并行代理会互相覆盖同一文件；写文件前先读回，不要相信自己在会话早期缓存的内容。
- 跨代理的分工要按文件边界切开（谁改哪个模块写清楚），否则 diff 归属无法判定。

### 降级落点：硬拦截 vs 可见降级

发现「状态陈旧/来源不可用」时，先回答**谁有权拦**，再决定写在哪里：

- 先追消费方是否会把它升级成永久阻断。本轮实例：`check_constitution` 返回 `allowed=False`
  → `decision_loop` 把它并进 `hard` 阻断 → FinalVerdict 永久 NO-GO；而该快照**没有生产者**，
  等于把系统锁死。正解是「可见降级」（来源矩阵一行 + 卡面标注），不新增硬闸门。
- 判据：**若该来源当前没有生产者能把它刷新回健康，就不能新增硬拦截**——那不是 fail-closed，是 fail-forever。
- 读取本身绝不回写文件、绝不用默认值补齐业务日期/余额；陈旧必须保持陈旧且可见。
- 历史遗留的模拟数据（如 `sim from monitor …` 的账户快照）不得当作已核对真实账户。

### 伪造默认值扫描（审计必查）

采集器里 `.get(<行情字段>, <数字默认>)` 是「看起来正常」的假数据来源。本轮实测：
VIX 取数默认 20 + SPX 默认 0 → 全源失败时照样打印「中性 | VIX 20 | SPX +0.0%」，
与来源矩阵的「未采到有效字段」自相矛盾。

- 扫描式样：`\.get\([^)]*,\s*[0-9]`，以及打印/渲染行里的默认值兜底（`or 100.0`、`{...或'?'}`、`change_pct, 0`）。
- 修法：只在真的取到字段时才写 `sentiment`/`level`/分类词，并盖**真实采集时间戳**让外层信封能报 `live`；
  取不到就明确写「本轮未采到有效字段」。
- 「中性」「持平」这类分类词也算输出：不能由缺失值 + 默认数推导出来。

### 看门狗误报类（报警疲劳）

盯错误的文件必然长期误报，最后把真事故淹掉。本轮实例：监控 `keylevels_structure_review.json`
（设计上只有 `{ok,valid,checked,stamped}`、无时间戳）→ 天天报「显式时间戳缺失」；
真实时间戳在 `keylevels_config.json` 的嵌套键 `auto_approval_policy.structure_reviewed_at`。

- 定监控清单前先确认**该文件里真的有可解析时间戳**；否则改指真正的时间戳所在（必要时支持嵌套键路径）。
- 现役关键文件缺失必须报异常，不能静默跳过。
- 看门狗默认只写本地报告；外发必须显式开关，并有独立环境 kill-switch 兜底。
- 缩短检查间隔前先确认脚本已无外发依赖（否则等于把外发频率提高 4-5 倍）。

### 计划任务恢复与节流纪律

- **恢复暂停链路前先定性**：同域常有多条链（本轮「影子结果标注」停摆，但「信号闭环·tick」仍在跑）。
  先搞清两条链各自的写入物与消费者，再决定恢复还是退役；不能因为名字像就合并或双写。
- **先跑一次再恢复**：`resume` 前手动跑一次并**量墙钟时间**。本轮实例：影子标注器单轮 20 分钟以上，
  远超原 `*/15` 的间隔——它很可能就是被自己拖死的，不是功能坏了。
- **恢复后要有运行回执**：`hermes cron run <id>` 触发一次，再核 `last_status=ok` / `last_run_at` /
  `hermes cron runs <id>` 有 completed 记录。只看 `enabled=true` 不算恢复成功。
- **收紧间隔前先确认脚本已无外发依赖**（否则等于把外发频率提高数倍）。

### 重复网络探测：探一次，缓存可用传输模式

对 N 个条目做同一个网络请求时，逐条重新探测传输模式（直连/代理）是最常见的隐性慢点。本轮实测：
同主机 Binance 直连固定 12s 超时、代理 0.44s 可用 → 111 条 × 12s ≈ 22 分钟，`*/15` 的 cron 永远跑不完。
修法：模块级记住**已探明可用的模式**并优先复用，另一模式给短超时作兜底；单轮降到 12 秒。

- 通用判据：**先量一次单调用延迟，再乘以条目数**，与调度间隔比较；不满足就先修脚本或改间隔。
- 首次探测仍要走一遍失败路径（否则换网络环境后无法自愈），但只走一次，不是每条都走。

### 上游端点退役与字段名迁移（静默归零）

**不要用「封装函数返回空」判定源失效**——先绕过封装直接探原始 URL，用 HTTP 码定性：

- `403` = 端点被上游下线/禁用；`402` = 套餐不含该符号；`429` = 限流（源级熔断）；`200 但空数组` = 符号写法/参数错。
- 本轮实例：`/api/v3/quote/{sym}` 全符号 403（已下线），而**同仓其他函数早已迁到 `/stable/quote?symbol=`**
  —— 「只有一个调用点还在用旧端点」是这类 bug 的典型特征：先横向 grep 同一上游域名，看谁已迁移。
- **字段名迁移会静默归零**：旧端点返回 `changesPercentage`，新端点返回 `changePercentage`（无 s）；
  只读旧名的代码拿到 `None → 默认 0`，涨跌幅长期显示 `+0.0%` 而无人报警。
  修法：两个名字都认，并对新端点做一次真实冒烟。
- 部分可用要如实分列：受限符号进 `unavailable_fields`，能取到的照常写入并盖时间戳
  —— **「一个符号失败」不等于「整个源不可用」**。

### 缓存层把失败洗成 live（矛盾状态的常见根因）

同一张卡上「来源矩阵写 live」+「管线审计写未采到有效字段」并不矛盾，往往是缓存层的锅：

- 通用 TTL 缓存把 fetcher 返回的**空 dict / 只含失败标记的 dict** 也当成功写盘；
  TTL 内后续调用命中缓存并返回 `status="cache"` —— 而 `cache` 通常属于 LIVE 状态集合。
- 修法三件套：① 空结果不入缓存；② 给调用方一个 `cache_when(payload)->bool` 判定；
  ③ 只有**真的取到至少一个字段**时才盖采集时间戳（时间戳同时决定外层能否报 `live`）。
- 判据：**「有缓存」≠「有数据」**。凡报 `live/cache` 的来源，都要追问一句「它的 payload 里有真字段吗」。

### 陈旧值配成功前缀 = 负资产

无生产者的本地快照文件不只是「少了一块」，而是会主动误导：

- 本轮实例：`data/x_sentiment_context.json` 停在两个月前（恐贪 25 / 市占 56.3%），
  而卡面用 `✅ X情绪: …` 打印它；今日真实恐贪是 62-63 —— 带 ✅ 的旧数比不显示更容易被当成当前值。
- 处置只有两条路：**接真源**（本轮 router 声明的是按需 `x_search`，实现却读本地文件 → 声明/实现漂移）
  或**在卡面明确写「陈旧·不采用」**。不要保留「✅ + 陈旧数」这种组合。
- 判据偏保守：一个只提供展示、且可能显示旧值的源，其价值要按**负分**起步，不是按零分。

### 人工输入型工具：dry-run 默认 + 拒绝编造

给「必须由人提供事实」的写操作（账户余额、对账日期）设计工具时的统一形状：

- 关键输入（如 `--balance`）必填且校验 `> 0`；缺失/非法直接拒绝，**绝不回落到默认值或旧文件值**。
- 默认 dry-run，只有显式 `--write` 才落盘（与看门狗 `--send` 同一约定）。
- 落盘采用「读原 JSON → 只覆盖自己拥有的字段 → 原子写」，而不是序列化 dataclass：
  否则 `last_unreviewed_trade` 这类非模型字段会被静默丢掉。
- 原文件损坏时拒绝覆盖（`raise SystemExit`），保留现场供人工检查。

### 加固变更与既有测试的取舍

- 优先选择**不让既有测试变红**的加固落点。本轮子代理的硬拦截让 5 个既有生产用例失败，
  改成可见降级后它们自然恢复绿灯——这本身就是「落点选错了」的强信号。
- 若确实要改既有契约，改前先问：这些用例编码的是**真实业务语义**还是**已过时的旧行为**？
  前者改实现，后者改用例；不要为了保住测试而保留不安全行为。
- 只改「本轮自己新增的测试」去适配新契约；动别人既有的用例必须有独立证据。

### 跨品种共享状态下的现场验证

共享图表只有一张：验证时**优先跑当前已显示的那个品种**，而不是把图切走去验另一个。
本轮 TV 在 `OANDA:XAUUSD 5m`（XAU 同步链持有），于是用 XAU 同步实跑来验证 XAU 证据链，
不为验证切到 BTC。若必须切，先核对身份并明确说明本轮截图属于哪个品种/周期。

## 外部检索与代理侧证据（x_search 类）

- **只收有出处的回答**：实测 `x_search` 带 `from_date/to_date` 过滤时返回 `degraded=true`、`inline_citations` 为空，
  且内容明显是幻觉（给出「阻力 112,000–114,000」而当时 BTC 现价 77,200）。判定规则：`degraded is false`
  且引用非空才可采用；随后把引用里的关键位与 Binance/TV 现价做**量级常识核对**，不通过就整条丢弃。
- **宁可没有情绪，也不能写错情绪**：检索结果是「仅情绪」证据，不得改写方向/仓位/价格；
  写入时必须自带「仅情绪·不改裁决」这类标签。
- **脚本抓不到的，交给 agent 按需做**：不要为「按需能力」硬造一个采集器。本轮形状：脚本负责可复现的客观部分
  （恐贪 / 市占 / 热门），agent 负责检索叙述并经显式参数（`--x-note`）写回**同一个文件**；
  agent 侧也要跑一遍 `--dry-run` 语义（脚本默认不覆盖已有叙述，除非显式传入）。
- **写入的文件必须自带可判龄时间戳**，消费方按龄决定「采用 / 不采用（旧值不展示）」；阈值写死在消费方，
  不靠人记得刷新。若顺手给该源加了一层「客观部分刷新」，它顺带能治另一类陈年问题（本轮：市占从 6 月的
  56.3% 换成真实的 58.7%）。
- 检索类源仍然受「降级可见」约束：取不到的子项保留旧值**并标 stale**，全子项失败才非零退出。

## 载荷字段名/类型与消费方约定的冲突

- 通用载荷检查器（`source_health.inspect_payload` 类）若约定某键是**单一状态字符串**，
  把结构化字典写进同名键会让 `x in VALID_STATES` 抛 `unhashable type: 'dict'`，**整条状态判定失败**
  （本轮实测：新增刷新器写了 `source_status: {...}` → 该源从 live 直接掉成 unavailable，
  卡面同时出现「✅ 打印正常」与「矩阵 unavailable」）。
- 修法两侧都做：① 调用方改用不冲突的键名（如 `refresh_status`）并清理历史遗留键；
  ② 检查器只采信合法类型（`isinstance(x, str) and x in VALID_STATES`），坏载荷不得炸整条链路。
- 通用判据：给既有 payload 加字段前，先 grep 该键名是否已被状态/健康判定占用。
- 同类信号：`unhashable type` / `TypeError` 出现在**状态判定**而不是采集器里 → 先怀疑键名与类型冲突，
  而不是去改采集逻辑。

## 全量回归的环境干扰（别把环境当回归）

- 全量套件会受共享状态干扰，本轮两个实例：①持有 TV 分析租约时 `test_keylevel_contract`
  的刷新路径如实「让路」→ 用例变红；②`binance_public` 的 host 冷却表是**模块级全局**，
  别的用例真连一次失败就把首个 host 关 300s → 后续用例少了一次调用。
- 因此：**跑全量前先释放分析租约**（`tv_analysis_lease.py end` 并核 `status` 为无租约）；
  单跑通过 / 全量失败 → 先怀疑共享状态与网络，再怀疑代码回归；不要急着改被测代码。
- 同轮不同的用例轮流红（不是同一个一直红）几乎一定是共享状态，而不是新引入的回归。

**修法是用例侧隔离，不是去改被测代码**（用户说「清理」时就是要这个）：

- 共享状态两类落点：①**模块级全局**（host 冷却表、内存缓存、健康标志）→ autouse fixture 逐用例复位；
  ②**外部副作用状态**（磁盘上的分析租约、锁文件）→ autouse fixture 把状态查询函数打成「无」。
- 打补丁要打在**查询函数所在模块**上：被测脚本常用**函数内 import**（`from tv_data_bridge import analysis_lease_status`），
  补丁打在调用方模块上无效。
- 补一条 canary 用例断言隔离生效（`assert bp._HOST_DOWN_UNTIL == {}`），否则同类泄漏将来只会以「别的用例偶发红」出现。
- **验收必须复现原失败条件**：本轮是「故意持有活跃租约（`remaining_seconds≈360`）再跑全量」→ 全绿；
  外加常规连跑 3 次都不飘。只跑一遍绿不算验证。
- 若泄漏源未能稳定复现，如实说明「落点选的是进程级隔离；元凶未定位」，不要假装找到了根因。
  详见 `references/external-search-evidence-and-freshness-gate-20260913.md` 第四节（含可用 fixture 代码）。

## 交付格式

先给总体结论和评分，再给短表格：运行态、P0/P1/P2、管线档位、TV/双指标、模板投递、优化顺序。若包含交易分析截图，截图首行并用本地绝对路径Markdown引用。报告只写已取证内容；缺少实盘收益、用户端可见性或云端编译回执时明确标“未验证”。

**「给出推荐优化」不等于停在建议清单**：用户说「按你的建议推进 / 把系统打造更好」时，
要真的落地修复 + 跑验证 + 标边界，而不是再交一份计划。

- 每条落地后给回执：测试数、实跑输出、提交号；不只说「已修复」。
- 被否掉的建议要写明**为什么否**（本轮否掉：风险状态硬拦截、机械重启停用采集器、
  「uv 3.12 缺包」这类不成立的结论），否则下一轮又会有人把它当成待办捡起来。
- 需要人工事实的建议（余额、真实成交）不替用户填数：落成默认 dry-run、拒绝编造输入的工具，
  由用户触发；在此之前系统如实标「状态陈旧 / 非真实额度」。
