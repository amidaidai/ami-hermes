# 外部审计的逐条取证（把「是不是」变成可执行修复清单）

## 适用

用户把一份外部审计（GPT／顾问／另一个 agent）贴过来问「你了解看看，是不是」时。
交付物是三样：**逐条判定表** ＋ **影响面校准** ＋ **按自己顺序的修复建议**。
不是复述审计，也不是照它的顺序改。

## 流程

1. **批量读锚点**：审计给的 `file:line` 先读上下文再表态（read_file 分批，别只读那几行）——锚点经常只对一半。
2. **每条跑一遍**再判定。两类**都要**跑：
   - 真实产物（现成的卡／日志／库）→ 证明**现状**；
   - 合成最小样本（手写卡、单行 DB 记录）→ 证明**当前生产不可达**的契约分支。
3. **判定分三类，一张表里都要出现**：`为真` / `不复现（写清为什么）` / `无法溯源`。
   审计给的「X 项测试通过」这类数字，先在仓库查出处（grep 文档）并跑一次全量拿自己的真实数；
   查不到就写「仓库无出处，无法复现；我实跑是 N」——**不要顺着用它的数字**。
4. **影响面校准决定优先级，不是审计的顺序**：
   - 这条路径**今天会被命中几次**？去信号/事件库里数（某裁决状态 0 次出现 = 缺陷「潜在不可达」，不是「正在误导」→ 降价但便宜就先修）。
   - 审计常把**告警台账的「未关闭」**读成「系统在故障」。台账语义要单独解释：哪几条是业务检测命中、哪几条是设计性让路、哪几条已自愈。
5. **弱结论要补强**：审计说「需核原始值」时，从代码链反推边界把它变成已定位结论
   （例：闸门 `>= 2.0` 判绿 + 显示 `:.1f` → 「不足1:2」与「1:2.0」并存只可能来自 1.95~2.0，是显示问题，不是闸门错）。
6. **给自己的顺序**：先修什么 / 为什么 / 影响面，并明确**不建议现在做**的（数据不支持就先算 WFO ＝ 产出不能采信的数）。
   用户说「按建议推进」= 按你的顺序执行。
7. **披露没做的**：明确说「第 N 项我没动」；「预检通过」不得扩写成「全系统验收通过」。

## 省时间的常见形态

- **同一事实往往有多份实现**：先 `grep -rn` 找全显示/格式化点再一次改完。只改一处，缺陷会在别的资产上原样复发
  （实测：价格格式化在三处渲染器各写一份，上游修好、下游取整，只在部分资产暴露）。
- **外部状态直接读，不靠转述**：Hermes 的 `executions` 表带每轮状态与 stderr；`cron_incidents` 是未关闭台账；
  两者对不上时以实跑记录为准。
- **「已恢复」要连续多轮证据**，单次成功不算；判定脚本必须能把「让路／业务命中」与「真失败」分开，
  否则会把设计性跳过记成故障。
- 审计里的「默认值/步数/口径不一致」要先核实现与文档哪一侧错，再决定改哪边（有时文档是对的，代码才是 drift）。

## 交付形状

先给结论（审计准不准），再给 `审计声明 | 我的实测 | 判定` 表（真假都列），
然后写「我的顺序 + 不做什么」，最后列未收口项与证据文件路径。
